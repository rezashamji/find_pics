(2) FLOAT PRECISION
  - How the phone computes P (Judge.swift pOf): logits of the last position -> .asType(.float32) -> softmax over the whole
    vocabulary in float32 -> py = sum over {yes, Yes, ' yes', ' Yes'}, pn = same for no -> P = py / (py + pn) in Float32 ->
    Double. So P = 1 / (1 + e^-g) with g = logsumexp(yes logits) - logsumexp(no logits). The server does the same from
    vLLM's top-20 logprobs; the stored P is float32.
  - Two limits, and the coarser one is the logits, not P:
    (a) The logits arrive in bf16. In the stored data every g is a multiple of 0.25 (65 distinct values, step 0.250
        everywhere = bf16's spacing for logits of size 32-64). Each step multiplies 1-P by 1.28. The phone's MLX bf16 logits
        should show the same grid, but that is UNMEASURED. Kernel differences of a step or two move 1-P by 1.3-1.6x.
    (b) Float32 P saturates. Below 1.0 its steps are 2^-24 (6e-8), so float32 P == 1.0 means g >= 17.5 on the grid
        (exactly 1.0 once 1-P < 3e-8). From g ~ 14 up, the float32 rounding of P already bends the grid (14.56, 14.69,
        15.03 ...). The largest finite g stored is 16.64.
  - Photos with P exactly 1.0: beach 230, food 83, sunset 20; dog, car, bicycle 0 (the object question never gets above
    g 16.6). These photos are all lumped together: the data cannot tell g = 17.5 from g = 30.
  - Can the phone tell 0.99999 from 1.0? Yes. 0.99999 is g = 11.5, about 24 bf16 steps and 168 float32 steps below 1.0.
    Only cuts at or above ~0.9999999 (g ~ 16) sit inside the saturation zone.
  - Probability cuts land between grid steps. The level g = 11.5 has P = 0.9999899 < 0.99999, so 'P >= 0.99999' actually
    means g >= 11.75. 0.999 = g 6.91 -> first kept level 7.0. 0.9999 = 9.21 -> 9.25.
  - RECOMMENDATION: make the rule a logit-gap threshold. Compute g = logsumexp(yes logits) - logsumexp(no logits) in
    float32 directly from the last-position logits; this needs no full-vocabulary softmax. Keep on g >= T: object T = 0.85
    (= P 0.7), subject T = 6.91 (= P 0.999). On the 0.25 grid these keep the levels >= 1.0 and >= 7.0, the same photos as today's P test. The threshold is then readable and free of float32
    saturation, and it would let a future cut above 17 mean something. P stays for display.
    Before trusting any cut above ~12 on the device: log g on the phone for ~50 photos the cluster scored and compare
    (phone-vs-cluster logit agreement is unmeasured).
JUDGE CUT SWEEP: precision AND recall of a stricter P(yes) cut, per search (public DISBench data; 2026-10-11)
Code: eval/eval_judge_cut_sweep.py (no model runs). Judge = Qwen3-VL-4B real phone 4-bit weights, stored float32
P(yes) on all 7,886 photos of the 4 RESULTS 34 libraries (eval/recall_audit/scores_q3vl4b_real), the planner's
questions: dog/car/bicycle = object form 'Is there a real X anywhere in this photo ...?' (phone cut today 0.7);
beach/sunset/food = subject form 'Is this a photo of X?' (phone cut today 0.99, JudgeCutoff.swift).

METHOD. RESULTS 34's estimator (eval_recall.score_systems). Its strata were NOT defined by the 0.99 cut: they are
the OLD simulated-weight judge (eval/recall_audit/scores) at P >= 0.7 (kept) / doubt / top-5% vector / rest, with
uniform blind draws inside each. Any keep rule on the REAL judge's P is scored by splitting every stratum into
cells by which cuts keep the photo (nested cuts -> cells = real-P bins within a stratum). A uniform draw inside a
stratum is uniform inside each cell, so each cell's real count = size x its labelled match rate; a cell with no
labelled photo takes its stratum's rate ('imputed' below). All cuts scored jointly = one shared total of real
photos, so recall at every cut has the same denominator. Earlier (non-uniform) eye labels count exactly.
  V1 = RESULTS 34 labels only (old + 1,950 blind) - the estimator exactly as RESULTS 34/45 ran it.
  V2 = V1 + RESULTS 45 census (526 audit4 census labels). The census covers a FIXED photo set per search (vector
       top 50 + judged top 50 of the pooled library, each library's vector top 20 + judged top 20), all labelled
       -> made an exact stratum; the uniform blind labels then estimate only the photos outside it. Main table = V2.
  'unsure' = not a match (as RESULTS 34/45); V2u = unsure counted as a match (sensitivity).
  Intervals: 95% stratified bootstrap (RESULTS 34; optimistic where a stratum shows 0 matches in its sample),
  recall also 95% Bayesian (Jeffreys per cell; the honest one for misses in the big rest stratum).
  Census screens per search: dog 114 photos (0 unlabelled), car 138 photos (0 unlabelled), bicycle 102 photos (0 unlabelled), beach 101 photos (0 unlabelled), sunset 120 photos (0 unlabelled), food 108 photos (0 unlabelled)

Cut -> yes-minus-no logit gap g = ln(P/(1-P)) (P = py/(py+pn), py/pn summed over yes/Yes/' yes'/' Yes' and no
variants): 0.7 -> 0.85, 0.99 -> 4.60, 0.999 -> 6.91, 0.9999 -> 9.21, 0.99999 -> 11.51, 0.999999 -> 13.82, ==1.0 -> 17.33 (float32 P is exactly 1.0 for g > ~17.3).
